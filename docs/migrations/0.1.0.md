# Migrate or reconcile to Morifolium v0.1.0

Morifolium upgrades are repository migrations, not framework dependency upgrades. v0.1.0 is the first immutable release, so this guide is primarily for pre-release adopters and existing mobile repositories evaluating the golden-path contracts.

## 1. Establish lineage

Record the target Morifolium version in the consumer repository:

```text
0.1.0
```

Keep the consumer's `.morifolium-version` file after local customization so later migrations have an explicit comparison point.

## 2. Adopt the canonical task boundary selectively

Expose one repository-owned validation command that developers and CI can both invoke. The reference profile uses:

```bash
mise install
mise run ci
```

Do not replace healthy stack-specific build tooling merely to copy Morifolium. Eyespie, for example, retained its existing Gradle setup and CI-specific caching while adopting the `mise` task boundary.

## 3. Reconcile security invariants

Compare the consumer's actual capabilities and threat model against the v0.1 reference defaults:

- cleartext transport denied unless a reviewed exception is required;
- backup/device transfer denied by default for application data;
- exported Android components explicit and minimal;
- validation jobs require no production credentials;
- signing material remains outside repository source.

Adopt equivalent controls when the capability exists. Do not copy configuration that protects a boundary the consumer does not expose merely for cosmetic consistency.

## 4. Reconcile observability

If the consumer has operational telemetry:

- minimize metadata before any sink/export boundary;
- keep operational telemetry distinct from product analytics;
- prevent optional telemetry failure from becoming application authority;
- preserve cancellation/interruption semantics;
- keep remote provider credentials, retention, consent, sampling, and residency consumer-owned.

A consumer with no telemetry requirement does not need to copy Morifolium's reference telemetry classes.

## 5. Preserve product ownership

Do not import Morifolium application code or overwrite product-specific architecture simply to match the reference fixture.

The consumer remains authoritative for:

- product behavior and domain architecture;
- identity/authentication and backend authorization;
- production data and privacy obligations;
- release signing/store publication;
- specialized integrations such as Digitalis or Envuscator.

## 6. Validate the consumer

Run the consumer's full validation gate after the reconciliation. Update `.morifolium-version` only after the consumer-specific checks succeed.

For Morifolium itself, the release gate is `mise run ci`. Consumers may use different underlying tools as long as CI and developers share the same canonical repository task boundary.

## Pre-release snapshot note

Pre-v0.1 Morifolium snapshots duplicated the version in `.morifolium-version` and the Android application's `versionName`. v0.1.0 makes the repository marker authoritative and derives the Android `versionName` from it. Consumers carrying both values should consolidate them rather than maintaining two independent version declarations.
